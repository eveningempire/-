# 20JD 后续实验与平台化路线

## 核心判断

首要瓶颈不是继续增加 Transformer/KAN 复杂度，而是缺少可识别真实 RUL 的 run-to-failure 生命周期数据、注册失效阈值和独立 unit 切分。现有 409 运行只能支持健康评估、代理趋势和 shadow 工程验证。

## P0：科学闭环

### 1. 审查已回传 R2/n2

- 核对数据、源码、配置、checkpoint 和预测 hash；
- 检查 train-only scaler、validation-only selection 和冻结后 test；
- 核查 negative teacher/control 和每个 seed 的证据；
- 报告多 seed 估计与置信区间，不只报最佳 seed；
- 审查前不把 candidate 标为 accepted/final。

### 2. 冻结 run-to-failure 数据合同

- 定义 `unit_id`、cycle/time、观测终点和删失原因；
- 失效阈值来自设计准则/FMECA/甲方规范，不从预期结果倒推；
- 同一 `unit_id` 的整个生命周期不跨 train/validation/test；
- 保留失效和右删失样本，先做小规模 pilot，再扩大数据生成；
- 数据版本保留 generator commit、仿真配置、seed、环境和 SHA-256。

## P1：平台端到端 shadow

1. 补齐“原始遥测 -> 窗口/特征 -> CDPCA/AE 证据 -> health adapter”；当前包从证据窗口开始。
2. health 和 RUL 统一 schema registry，但保留独立 contract/version，禁止隐式改名或重排。
3. 完成 API/进程包装、超时、并发、日志、provenance、热切换和回滚。
4. 录制数据 shadow replay，测端到端延迟、吞吐、缺失/乱序处理和弃权率。
5. UI 明示 `shadow`、`actionable=false`、`physical_rul_claim=false` 和 abstain reason。

## P2：有合法标签后的 RUL 实验

1. 预注册 MAE/RMSE、早晚预测非对称代价、校准度、分位误差、工况/部件分层和 bootstrap CI。
2. 先跑 HI 趋势/统计模型、MLP、LSTM、BiLSTM 可解释基线。
3. validation 选一个候选并冻结，test 只评估一次，关键结论跑多 seed。
4. 基线闭环后才做 TCN/Transformer/KAN/蒸馏消融，要求收益稳定且成本可解释。
5. 重点验证跨 unit、工况和故障模式泛化，避免相邻窗口泄漏。

## P3：上线门槛

- health fault alarm 达到预注册门槛，localization 阈值注册并独立验证；
- RUL 不再是 `PROXY_ONLY / ALL_CENSORED`，物理含义经专业人员签字；
- 完成 OOD、校准、不确定性、弃权、故障注入、硬件在环和回滚；
- shadow -> advisory -> actionable 分阶段审批。

## 近期顺序

1. R2/n2 科学审查；
2. run-to-failure 合同与数据 pilot；
3. 师弟完成原始遥测到 health/RUL shadow 的平台接口；
4. pilot 通过后扩展 unit、失效模式和工况；
5. 锁数据版本后执行基线 -> 候选冻结 -> 一次 test -> 平台 replay。
